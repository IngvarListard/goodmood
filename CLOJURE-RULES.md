## 1. Технологический стек проекта

- **Backend**: Clojure 1.12, Ring + Jetty, Reitit (роутинг), Integrant (жизненный цикл)
- **База данных**: SQLite через next.jdbc + HoneySQL v2, миграции через Migratus
- **Валидация**: Malli (схемы как данные, интеграция с Reitit)
- **Сериализация**: Muuntaja (content negotiation)
- **Рендеринг**: Hiccup v2 (SSR), HTMX (ajax-взаимодействие), Hyperscript (инлайн-скрипты)
  - Импорт: `[hiccup2.core :refer [html raw]]`. `html` для рендеринга (автоэскейпинг), `raw` для сырого HTML.
  - **Не используй `hiccup.core`** — в v2 он deprecated.
- **Стили**: Tailwind CSS + DaisyUI
- **Сборка**: deps.edn (без ClojureScript, без shadow-cljs)

Reason: правила должны отражать реальный стек, а не гипотетический. В проекте нет ClojureScript — фронтенд строится на Hiccup SSR + HTMX + Hyperscript.

## 2. Архитектура системы

### 2.1 Общий поток данных

Следуй модели "Request → Handler → Domain → Response", где вся бизнес-логика — чистые функции от данных, а side-effects вытеснены на края системы:

```
Request (Ring map)
    │
    ▼
Reitit Router ── парсинг URL, параметры, middleware
    │
    ▼
Handler (app.routes.*) ── извлекает ds из system, вызывает domain
    │
    ▼
Domain (app.domains.*) ── чистые функции, malli-схемы, оркестрация
    │
    ▼
DB (app.db.*) ── honeysql-запросы, next.jdbc
    │
    ▼
Views (app.views.*) ── data → hiccup (только чистые функции)
    │
    ▼
Response (Ring response map, HTML или JSON)
```

- Router (Reitit) принимает HTTP-запрос и превращает его в data-map.
- Handler извлекает зависимости из system и вызывает domain-функции.
- Domain-функции — чистые трансформации данных, не знающие про HTTP или Ring.
- Views — чистые функции `data → hiccup`, без side-effects.
- Ответ собирается в Ring-response на границе (в handler), а не в глубине domain/view.

### 2.2 Структура слоёв в `src/app/`

Файловая структура — слоистая. Каждый слой знает только о слоях "ниже": `routes` → `domains` → `db`, результат идёт в `views`. Подробнее см. `openspec/context/03-architecture.md`.

| Слой | Путь | Технология | Запрещено |
|---|---|---|---|
| Routing + Handlers | `src/app/routes/` | Reitit + Ring | SQL, hiccup-разметка внутри handler |
| Domain | `src/app/domains/` | Чистый Clojure + Malli | ring-request/response, hiccup, reitit |
| Persistence | `src/app/db/` | HoneySQL + next.jdbc | hiccup, ring-request/response, reitit |
| Views | `src/app/views/` | Hiccup v2 | SQL, бизнес-валидация, db-вызовы |
| System | `src/app/system.clj` | Integrant | Бизнес-логика |

**Правила слоёв:**

1. Не импортировать "снизу вверх": `db` не должен требовать `routes`/`views`/`domains`.
2. Новую бизнес-логику класть в `domains/`, а не в хендлер роута.
3. Вьюха всегда принимает готовые данные, а не сама их достаёт.
4. Один домен — одна поддиректория в `domains/`, если доменов больше одного.

### 2.3 SQL как данные

SQL-запросы живут только в `src/app/db/`. Они строятся как honeysql-карты, не строки:

```clojure
;; хорошо — honeysql map
(sql/format {:select [:*] :from [:entries] :order-by [[:date :desc]]})

;; плохо — сырая SQL-строка
"SELECT * FROM entries ORDER BY date DESC"
```

Reason: honeysql-карты — это данные. Их можно тестировать без БД, композировать, проверять на структуру, и они защищены от SQL-инъекций на уровне API.

### 2.4 Фронтенд (HTMX + Hyperscript + Tailwind/DaisyUI)

Фронтенд строится без ClojureScript. Интерактивность достигается через:

- **HTMX**: атрибуты `hx-post`, `hx-get`, `hx-target`, `hx-swap`, etc. для ajax-взаимодействия
- **JSON Enc**: расширение `hx-ext="json-enc"` для отправки JSON
- **Hyperscript**: атрибуты `_` для инлайн-поведения (например, `_ "on htmx:afterRequest ... me.reset()"`)
- **Tailwind + DaisyUI**: классы для стилизации (`btn btn-primary`, `card bg-base-200`, `input input-bordered`, etc.)

Server отвечает HTML-фрагментами (partials) для HTMX-запросов и полными страницами для обычных.

```clojure
;; HTMX-детекция в handler
(defn htmx-request? [request]
  (= "true" (get-in request [:headers "hx-request"])))

;; Content negotiation: HTML для браузера, JSON для API
(defn- prefers-html? [request]
  (clojure.string/includes?
   (or (get-in request [:headers "accept"]) "")
   "text/html"))
```

### 2.5 Управление состоянием (Integrant)

Используй Integrant для управления жизненным циклом компонентов. Граф зависимостей — EDN-данные, не код:

```clojure
(def system-config
  {:db/connection {:path "resources/goodmood.db"}
   :db/migrate {:connection (ig/ref :db/connection)}
   :app.core/server {:port 3000
                     :connection (ig/ref :db/connection)}})
```

- Зависимости передаются явно через параметры/контекст — никаких глобальных stateful-ресурсов.
- Не оборачивай domain-логику в `defprotocol` "на будущее" — протоколы только где нужна полиморфная подмена (например, адаптер к внешнему API).
- Не используй `def` для мутации в рантайме.

### 2.6 Ports & Adapters — точечно, не тотально

Применяй паттерн "порт-адаптер" для внешних зависимостей, но не для внутренней domain-логики:

- Порт — `defprotocol` или map функций, описывающая контракт.
- Адаптер — реализация (SQLite через next.jdbc, in-memory для тестов).
- В тестах подставляй fake-адаптер вместо реального — быстрые unit-тесты без БД.
- Не создавай порт для всего — если функция имеет единственную реализацию и нет нужды в подмене, протокол избыточен.

### 2.7 Миграции (Migratus)

Миграции лежат в `resources/migrations/`. Каждая миграция — SQL-файл с `-- up` и `-- down` секциями. Запуск — через `app.db.migrate/migrate!` при старте системы.

Reason: миграции — часть инфраструктуры, а не бизнес-логики. Они применяются один раз при старте.

## 3. Контракты данных: валидация на границах

Валидируй данные **на границах системы** — при HTTP-входе и выходе из БД. Внутри системы данным можно доверять.

- Используй **Malli** как основной инструмент. Схемы — данные, переиспользуются между валидацией входа и документацией.
- Для инвариантов внутри domain-функций используй `:pre`/`:post` (см. `CODESTYLE.md`). Это дёшево и не требует зависимостей.
- Не бросай "голые" исключения для ошибок валидации — возвращай структурированные данные (`{:error/type ... :error/message ...}`) или `ex-info` с map.

```clojure
;; Malli-схема для записи настроения
(def create-entry-schema
  [:map
   [:activity :string]
   [:effect :string]
   [:mood_score [:int {:min 0 :max 10}]]
   [:sleep_hours [:maybe :double]]])
```

## 4. REPL-driven development

- Создай неймспейс `dev` (в корне `src/` или отдельно в `dev/`) с функциями `start`, `stop`, `reset` для перезапуска системы, а также хелперами для сид-данных.
- Используй **Rich Comment Forms** `(comment ...)` для экспериментов — они остаются в файле и воспроизводимы.
- После изменения в файле переоценивай изменённую top-level форму, а не весь файл.
- Reloaded workflow должен быть явным: `(start)`, `(stop)`, `(reset)`.

## 5. Тестирование

- Тестируй прежде всего чистые domain-функции — это самая быстрая и надёжная часть test suite.
- Для side-effect-кода подставляй fake-адаптеры, избегая реальных сетевых/БД вызовов в unit-тестах.
- Храни тестовые данные в EDN-файлах рядом с тестами.
- Названия тестов — поведенческие спецификации ("returns error when mood score is negative"), а не технические ("test-1").
- Группируй связанные утверждения под `testing` для контекста в выводе ошибок.

Детальные конвенции тестов — в `CODESTYLE.md`.

## 6. Правила для AI-агентов

### 6.1 Два режима работы

При работе с кодовой базой агент различает два контекста:

| Контекст | Как действовать |
|---|---|
| **Имплементация одобренного ченджа** (есть `openspec/changes/<name>/` с `proposal.md`, `tasks.md`) | Следуй плану. Решения о зависимостях, архитектуре, схеме БД уже приняты в proposal/design. **Не переспрашивай** — реализуй. Сообщай только о найденных конфликтах или ошибках в плане. |
| **Спонтанная работа вне ченджа** (прямой запрос, нет активного proposal) | Применяй правила "Спросить сначала" из раздела 6.3. |

Reason: SDD-воркфлоу разделяет принятие решений (proposal) и исполнение (tasks). Переспрашивать на этапе исполнения — значит дублировать уже сделанную работу.

### 6.2 Всегда

- Следовать `CODESTYLE.md` для форматирования, отступов, именования.
- Валидировать данные на границах через Malli-схемы.
- Оставлять side-effects на границах (handler, adapter); домен и views — чистые.
- Использовать honeysql-карты для SQL, не строки.
- После изменений проверять компиляцию/тесты. Прогонять код через REPL.

### 6.3 Спросить сначала (только вне SDD-ченджа)

- Изменение схемы БД / создание миграций.
- Добавление новой внешней зависимости в `deps.edn`.
- Изменение архитектурного паттерна в существующем модуле.
- Рефакторинг без явного запроса.

### 6.4 Никогда

- Не использовать `def` внутри функций.
- Не шадоуить имена `clojure.core` локальными биндингами.
- Не создавать `defprotocol`/абстракции без конкретного кейса подмены.
- Не хранить состояние в глобальных atom'ах — только через Integrant system.
- Не коммитить секреты, токены, реальные строки подключения.
- Не хардкодить SQL-строки — всегда через honeysql-карты.

## 7. Взаимодействие с другими файлами конвенций

```
CLOJURE-RULES.md       — архитектура, стек, AI-правила (этот файл)
CODESTYLE.md           — форматирование, именование, идиомы Clojure
AGENTS.md              — инструкции по запуску, стек проекта, конвенции фронтенда
openspec/context/*.md  — архитектурные инварианты, контекст иконок
```

**CLOJURE-RULES.md не дублирует CODESTYLE.md.** При конфликте правил — CODESTYLE.md приоритетнее в вопросах форматирования/идиом, CLOJURE-RULES.md — в вопросах архитектуры и AI-поведения.

При изменении практик обновляй соответствующий файл в том же коммите.

## 8. Структура файла

- Файл описывает: стек проекта, архитектурные конвенции, AI-правила.
- Не дублирует CODESTYLE.md — ссылается на него.
- Каждое неочевидное правило снабжено `Reason:`.
- При росте файла свыше ~200 строк — выносить специфику в `docs/`.
