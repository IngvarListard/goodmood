# Оркестратор: ночной батч (6 change'ов)

> Владелец ставит реализацию на ночь и уходит. Основная сессия запускает этот
> файл и работает автономно до конца. Реализацию выполняют сабагенты, основную
> сессию не засоряем. Вопрос владельцу задаётся **только** если задача
> действительно не решается (см. «Эскалация»).

## Роль

Ты — оркестратор. Проведи 6 изменений OpenSpec от начала до конца без участия
человека. Каждый change — отдельный коммит и `openspec archive` после зелёной
верификации. Если стоп — пиши отчёт и останавливайся (см. «Эскалация»).

## Порядок (СТРОГИЙ)

```
1. fix-push-subscription        изолирован, высокая ценность, без миграций
2. add-aggression-axis          фундамент (миграция 004 + ось); нужен для 3
3. replace-radar-with-time-chart зависит от 2 (композит и dataset aggression)
4. entry-actions-from-feed      правит карточку ленты; до 5
5. feed-pagination              зависит от 3 и 4 (финальная лента/карточка)
6. fix-horizontal-overflow      финальная гигиена по всем view; последним
```

Почему так: сначала независимое и дешёвое (1), затем фундамент данных (2),
затем зависящее (3), затем карточка (4), затем переиспользующая её пагинация (5),
затем сквозная уборка overflow по уже финальной разметке (6). Не выполнять
зависимый change, если его зависимость не прошла (см. «Эскалация»).

## Предусловия (проверить ДО старта, иначе СТОП)

1. `git status --porcelain` должен быть **пуст** (нет незакоммиченного WIP).
   Если грязно — не запускать ночной прогон: записать это в отчёт и
   остановиться (владельцу нужно сначала закоммитить/сохранить WIP).
2. Создать рабочую ветку: `git switch -c overnight/batch-2`.
3. Не пушить, не деплоить (см. «Запрещено»).
4. Прочитать один раз: `AGENTS.md`, `CODESTYLE.md`, `CLOJURE-RULES.md`,
   `openspec/config.yaml`, `openspec/context/03-architecture.md`.

## Цикл на каждый change

1. `openspec status --change <name> --json` — убедиться, что `applyRequires`
   (только `tasks`) готовы; артефакты уже созданы.
2. Прочитать по порядку: `proposal.md` → `design.md` → `specs/**/spec.md` →
   `tasks.md`. Решения design.md — источник истины, не пересматривать.
3. Каждую задачу `tasks.md` выполнять через task-сабагента
   (`subagent_type: general`). Один сабагент = одна задача (или одна мелкая
   связная группа задач одного файла). Параллелить независимые задачи можно,
   но правки одного файла — только последовательно.
4. После задач — верификация оркестратором **лично** (см. гейты ниже).
5. Коммит на change (стиль репозитория: `git log --oneline -10`).
6. `openspec archive <name>`.
7. Если change правит `src/app/routes/app.clj` или `src/app/system.clj` —
   перезапустить приложение (эти правки не подхватываются `:reload`).

### Правила делегирования сабагентам

- Промпт сабагента — САМОДОСТАТОЧНЫЙ (он не видит твою сессию). Вкладывай:
  - текст задачи из `tasks.md` целиком;
  - точные пути файлов и референс-строки (из design.md);
  - критерии приёмки и команду проверки из задачи;
  - указание прочитать `AGENTS.md`, `CODESTYLE.md`, `CLOJURE-RULES.md`;
  - правило: правки `.clj/.cljc/.cljs` — через clojure-mcp (`clojure_edit`,
    `clojure_edit_replace_sexp`, `paren_repair`); :reload неймспейса после
    правки; комментарии по-русски, логи по-английски;
  - правило: **не менять** htmx/hyperscript-контракты, имена полей формы и
    CSS-классы, если задача не об этом.
- Сабагент возвращает: изменённые файлы + что проверил + отклонения.
- Если сабагент не прошёл верификацию — повтори задачу один раз с выводом
  ошибки. Вторая неудача → эскалация.

### Верификация оркестратором (лично, не делегировать)

Базовые команды (канонные):

```
clojure -M:test                      # юнит/роут-тесты (из корня репо)
./bin/dev                            # приложение :3000 + nREPL :7890
curl -s http://localhost:3000/       # → OK
cd e2e && npm run test:fast          # e2e без AI (~2.5 мин) — целевой цикл
cd e2e && npx playwright test tests/<spec>.ts   # один спек
```

- Playwright MCP: открывать затронутые страницы, кликать, проверять htmx-свапы,
  обе локали (`gm-locale=ru` / `gm-locale=en`), тёмную тему (`gm-theme=dark`).
- Мержить и коммитить только после зелёной верификации.
- Полный `cd e2e && npm run test` (с AI, ~6 мин) — один раз в самом конце
  батча, не в каждом цикле.

## Эскалация к человеку — ТОЛЬКО если

Владелец спит. Эскалируй (создай `openspec/changes/_orchestration-BLOCKED.md`
с описанием, затем СТОП — не идти в зависимые change'ы) только при:

1. задача не проходит верификацию после **двух** честных попыток ремонта (с
   полным выводом ошибки);
2. требуемая правка противоречит `design.md`/spec change'а, и безопасного
   дефолта нет;
3. нужна новая зависимость (не одобрена заранее);
4. миграция грозит потерей данных сверх описанного в change'е;
5. нужно сломать существующий htmx/hyperscript/поле-контракт, который задача
   не уполномочила менять.

Во всех остальных случаях — решай сам, выбирай безопасный дефолт из
артефактов, фиксируй отклонение в отчёте и продолжай. Не блокируйся из-за
косметики/UI: следуй дефолтам design.md. Не задавай вопросов, ответ на которые
выводится из артефактов.

- Сырой JavaScript, кроме уже санкционированных файлов
  (`resources/public/js/push.js`, `resources/public/js/feed-chart.js`,
  `resources/public/sw.js`) и только в рамках задачи.

- Правки light-темы (`[data-theme=light]` в `layout.clj`) — не трогать.
- Секреты в коммитах; правки файлов вне разрешённых задачей без причины
  (причина — в отчёте).
- Скриншоты/пиксельная сверка (дизайн не устоялся).
- Правка задеплоенных миграций `001`–`003` (`openspec/specs/*` правятся только
  через `openspec archive`).

## Отчёт (пишется в конце, `openspec/changes/_orchestration-report.md`)

- Таблица: change | статус (`archived` / `blocked` / `skipped`) | commit hash |
  чем верифицирован | отклонения.
- Список оставшихся (неархивированных) change'ов и почему.

- Точные команды прогонов и их результат (кратко: зелёно/красно).
- Если был BLOCKED — ссылка на `_orchestration-BLOCKED.md`.

## Вне прогона (deferred, НЕ выполнять)

- `notifications-history-page` (страница-история уведомлений) — отдельный
  change, требует решения владельца по хранению и read-статусу.
