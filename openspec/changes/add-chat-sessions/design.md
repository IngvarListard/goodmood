# Design: add-chat-sessions

## Context

`ai_chat_messages` — одна лента на юзера; `chat-history` берёт последние 8 сообщений и для UI (`GET /ai/chat`), и для контекста модели (`chat-reply`). Спека `users-auth` («Session expiration») описывает серверную проверку срока и replay-инвалидацию, которых в коде нет (проверено grep'ом): enforcement фактически браузерный (`max-age 3600`).

## Goals / Non-Goals

Goals: полный контекст текущей сессии для модели; «новый чат»; сессия логина 90 дней.

Non-Goals: compact истории; список прошлых сессий; sliding-продление; серверная enforcement срока сессии.

## Decisions

### D1. Сессия = колонка, «текущая» = максимальная

```
ai_chat_messages + session_id INTEGER NOT NULL DEFAULT 1
текущая сессия юзера = MAX(session_id)          ← указатель не хранится
«новый чат»          = session_id = MAX+1        ← строки-сессии не нужны
контекст модели      = все строки WHERE user_id AND session_id = текущая
UI истории           = те же строки
```

- Без таблицы сессий: список сессий не нужен (non-goal), а MAX+1 даст уникальность достаточную для одного юзера (одновременный «новый чат» из двух вкладок просто создаст два id — оба валидны).
- Миграция: существующие сообщения = сессия 1 (DEFAULT), history не теряется.
- Альтернатива (таблица chat_sessions с указателем в users/cookie) — отвергнута: пока нет UI истории сессий, таблица и указатель — мёртвый вес.

### D2. Контекст модели — вся текущая сессия, без cap

`chat-reply` получает все сообщения текущей сессии (ORDER BY id). Owner-решение: без cap; compact — будущий change. Стоимость: токены растут линейно в пределах разговора — приемлемо, разговор ограничен тем, что юзер нажал «новый чат».

### D3. «Новый чат» — POST /ai/chat/new, свап панели

- Кнопка в шапке ассистента рядом с крестиком (icon `plus`, i18n «Новый чат»).
- `hx-post /ai/chat/new` → domain создаёт новую сессию (MAX+1), ответ — свежий `#assistant-body` (пустая история, composer) через outerHTML.
- Без confirm: ничего не удаляется, старая сессия остаётся в БД.

### D4. Сессия логина — 90 дней, браузерная enforcement

`session-config`: `:max-age 7776000`. Не скользящая (отсчёт от логина; ring перезаписывает куку только при изменении session-мапы). Серверной проверки срока нет и не добавляем — cookie-store stateless, replay прежней куки возможен до истечения Max-Age; с 90-дневным сроком и low-risk доменом сознательно принимается.

**Spec rot, фиксируем дельтой**: старый текст «Session expiration» требовал серверную проверку issuance-timestamp и replay-инвалидацию — не реализовано и не было. Дельта описывает фактическую модель: срок 90 дней через Max-Age, logout очищает куку. Если replay-защита когда-нибудь понадобится — отдельный change (серверный timestamp в session-мапе + middleware).

## Risks / Trade-offs

- [MAX+1 при гонке двух вкладок] → обе сессии валидны, семантика не ломается
- [Полная история → рост токенов] → owner-решение без cap; compact отложен явно
- [90-дневная кука = долгий токен] → stateless по дизайну; секрет ротации логирует всех — как и сейчас
- [Миграция DEFAULT 1] → существующие сообщения остаются доступны в сессии 1, поведение «до/после» для старых юзеров не меняется

## Migration Plan

`002-chat-sessions` (up: ADD COLUMN + обратимый down: SQLite 3.35+ поддерживает DROP COLUMN). Старые сообщения остаются в сессии 1 — для юзера чат выглядит как раньше, кнопка «новый чат» начинает сессию 2. Откат кода — revert; откат миграции — down.sql.
