# Design: add-period-radar

## Context

Радар ленты (`app.views.rose/radar`, canvas 200×200 + `radar.js`) рендерится в `hero-card` для последней записи дня. Контракт `radar.js`: `canvas[data-gm-radar] = JSON {labels, values}` — данные и тексты генерирует сервер, пиксели — клиент. Это значит, что для периодов меняется только то, **что** кладут в values; рендер не трогается.

## Goals / Non-Goals

Goals:
- Радар за период: день (дефолт) / неделя / скользящие 30 дней
- Агрегация без искажений частоты логирования и «старое = свежему»
- OOB-переключение без перезагрузки

Non-Goals:
- ±σ разброс, советы по агрегату, изменения `week-chart`, изменения `radar.js`

## Decisions

### D1. Формула агрегации: среднее по дням → взвешивание свежести

Двухступенчатая:

```
Шаг 1 (по дням):   axis(day) = mean(непустых значений оси за день)
Шаг 2 (по периоду): value = Σ axis(d)·w(d) / Σ w(d),
                    w(d) = 0.5^(возраст_дня / полураспад)
Полураспад: день → равные веса; неделя → 7/3 ≈ 2.3; месяц → 30/3 = 10
```

Чинит два искажения простого среднего:
1. *Частота логирования коррелирует с тяжестью* — 5 записей тревожного дня не должны весить ×5. Шаг 1 даёт каждому дню равный вклад.
2. *Старые записи = свежим* — «состояние сейчас» ближе к последним дням. Шаг 2 с экспоненциальным затуханием.

Пример (неделя, сегодня вс): дни `[пн 3, вт 5, сб 8]` → простое среднее 5.3, взвешенное ≈6.7 — «неделя закончилась на подъёме», что и есть правильный ответ на «как я сейчас».

Альтернативы (отвергнуты):
- *Медиана/усечённое среднее* — устойчивы к выбросам, но в этом домене выброс — клинический сигнал (пик тревоги 9 не должен растворяться).
- *Смесь среднее+пик* — семантика числа мутнеет.

Edge cases:
- День с одной записью = сама запись → дефолт неотличим от текущего поведения
- nil-оси (записи до миграции 004) не участвуют в mean своей оси; ось без значений за весь период → 0
- Период без записей → нули (решение владельца), aria-label «нет данных»
- Записи с датой из будущего (дата редактируема) → исключаются из любого периода

### D2. Скользящие окна, считаем по `:date`

- День: `:date = сегодня`
- Неделя: `:date ∈ [сегодня−6; сегодня]` (7 дней, как `week-dates` в feed.clj)
- Месяц: `:date ∈ [сегодня−29; сегодня]` (скользящие 30, решение владельца)
- Все фильтры по полю `:date` (user-значимое), не по `created_at`: редактирование даты перемещает запись между периодами — ожидаемо.

### D3. Переключение — серверный фрагмент, htmx OOB

`GET /feed/radar?period=day|week|month` → фрагмент: canvas + подпись периода + кнопки-переключатель с `aria-pressed`. Свап `outerHTML` контейнера радара (`hx-swap-oob` в ответе hero не нужен — радар грузится со страницей, кнопки сами делают `hx-get` с `hx-target="#radar-period"`, `hx-swap="outerHTML"`).

- Кнопки — `btn btn-xs`/`btn-ghost`, daisyUI, активная — подсвечена
- Состояние периода не сохраняется (перезагрузка страницы → день) — сознательно: дефолт «сегодня»
- period — маленький enum, невалидное значение → день (404 не нужен)

### D4. Слои

- Агрегация — чистая функция в домене (рядом с `state-label` в `app.domains.entries`): `entries → period-axes`, тестируется без БД
- view-функция принимает готовые значения осей + период → hiccup; i18n-метки внутри view
- route: достаёт entries юзера, вызывает домен, рендерит фрагмент
- Подпись «среднее с учётом свежести» — i18n-ключ (`:feed/radar-weighted`), не «среднее» — честность формулы в UI

## Risks / Trade-offs

- [Формула неочевидна пользователю] → подпись «среднее с учётом свежести»; подробности — в этом design.md
- [Полураспад «период/3» — эвристика] → константы в одном месте домена; если визуально врёт — крутится без изменения контракта
- [OOB-свап canvas → `radar.js` перерисует?] → скрипт уже вешается на `htmx:afterSettle` (паттерн hero-свапов), `data-gm-drawn` сбрасывается вместе с новым canvas — проверить в e2e
