# Design: add-synology-deploy

## Context

Приложение — single-user трекер настроения на Clojure (ring/jetty, SQLite, migratus), сейчас запускается только на ноутбуке разработчика через `clj -M:dev`. Целевой хост — Synology DS224+ (x86_64, Celeron J4125, 2 ГБ RAM) с Docker/Portainer, доступен по SSH; уже обслуживает другие сервисы через reverse proxy DSM с Let's Encrypt (пример — FreshRSS). Ноутбук: x86_64, JDK 25, Docker 29. Архитектуры совпадают — кросс-компиляция не нужна.

Текущее состояние: конфигурация захардкожена (`system.clj`: порт 3000, путь `resources/goodmood.db`), env-переменные читаются точечно через `System/getenv` (session secret, admin seed, OpenRouter), 13 миграций применяются при старте через integrant `:db/migrate`, в dev-БД только e2e-данные.

## Goals / Non-Goals

Goals:
- Деплой одной командой с ноутбука на NAS, включая бэкап БД и health-check.
- Детерминированный подъём с нуля: пустая БД → фиксированный юзер + тестовая рыба.
- Честная политика миграций для прод-данных (append-only после первого деплоя).

Non-Goals:
- CI/CD, registry, zero-downtime, HTTPS на уровне приложения, off-site бэкапы, scheduled-бэкапы (см. Open Questions).

## Decisions

### D1. Дистрибутив: uberjar в JRE-образе
Uberjar собирается tools.build'ом локально; образ `eclipse-temurin:25-jre` (не alpine — glibc-совместимость без сюрпризов), non-root юзер, `-Xmx384m`.
- native-image/GraalVM отклонён: не нужен, есть риск несовместимости зависимостей (рефлексия), выигрыш в старте ~1.5 сек не окупается.
- Сборка образа на NAS отклонена: слабый CPU не проблема для `COPY jar`-образа, но тогда деплой зависит от ветки исходников на NAS; проще держать весь цикл на ноутбуке.
- Heap-лимит обязателен: NAS с 2 ГБ RAM уже несёт другие сервисы; дефолтная JVM-куча (¼ RAM) недопустима.

### D2. Доставка образа: `docker save | ssh docker load`
Один пайп, без registry и без Portainer в критическом пути. Portainer остаётся как UI для ручных stop/restart (stack можно импортнуть из compose), но деплой идёт через SSH.
- SSH-доступ к docker'у на NAS сейчас через sudo. Решение: добавить ssh-юзера в docker group — для домашнего NAS с единственным админом это приемлемо (root-эквивалент и так есть через ssh+sudo; group лишь убирает пароль). Альтернатива — NOPASSWD-sudoers для docker (тот же риск) или ввод пароля раз в деплой; выбор за пользователем, скрипт работает в обоих вариантах.

### D3. Миграции: применяются при старте контейнера (как сейчас)
Отдельный migrate-шаг/init-container не нужен: миграции уже вшиты в integrant-старт. Если миграция падает — контейнер не поднимается, health-check в deploy.sh это ловит и возвращает non-zero.
- Порядок в deploy.sh: stop → backup → up → health-check. Даунтайм = между stop и health-check'ом (секунды), для single-user приемлемо.

### D4. Squash: 13 миграций → `001-init`, одноразово
Конкатенация `.up`-файлов по порядку (финальная схема эквивалентна текущей — проверить на пустой БД), `.down` — дроп таблиц в обратном порядке. Dev-БД и e2e-данные пересоздаются seed'ом/скриптами. После первого деплоя — append-only: задеплоенные файлы read-only, деструктив только новой миграцией. Правила фиксируются в AGENTS.md.

### D5. Конфигурация: dotenv поверх `System/getenv`
Одна точка: `(def env (merge (dotenv ".env") (System/getenv)))` — реальный env сильнее файла; в контейнере `.env` не используется, всё через `env_file:` compose. В `system.clj` добавляются `GOODMOOD_PORT` (default 3000) и `GOODMOOD_DB_PATH` (default `resources/goodmood.db`), существующие `GOODMOOD_SESSION_SECRET`/`GOODMOOD_ADMIN_*`/`OPENROUTER_API_KEY` остаются как есть, но читаются через общий env. Файл `OPENROUTER_API_KEY` в корне репо упраздняется → `.env` (gitignored) + `.env.example` (committed).
- Библиотека — минимальный dotenv-парсер с Clojars (точную актуальную выбрать при имплементации по конвенции «последняя версия»); писать свой парсер не нужно, но и тяжёлый cprop/aero не оправданы для KEY=VALUE.

### D6. Seed: фиксированный юзер + рыба на пустой БД
Расширение текущего `seed-admin!`: при пустой таблице users создаётся админ из `GOODMOOD_ADMIN_EMAIL`/`GOODMOOD_ADMIN_PASSWORD` и добавляются тестовые данные (несколько записей за последние дни, ≥1 инсайт, ≥1 медикамент с расписанием) — чтобы свежий деплой можно было визуально проверить. Идемпотентно: если юзеры есть — ничего не делает (прод-данные не трогаются никогда).
- Обоснование «рыба всегда»: пользователь — единственный юзер приложения, ему нужен живой фид сразу после чистого подъёма (в т.ч. для проверки деплоя); избыточные записи удаляются в UI за секунды.

### D7. Бэкап: file-copy при остановленном контейнере
`cp db+wal+shm → backups/<timestamp>.db*` после stop, до up. Без `sqlite3 .backup` и без онлайн-копирования: приложение всё равно рестартует, копия на остановленной БД консистентна. Retention 10 (по `ls -t | tail -n +11 | xargs rm`). БД и бэкапы живут в bind mount `/volume1/docker/goodmood/{data,backups}` — видны Hyper Backup'у NAS и не пропадают с контейнером.
- WAL-момент: после штатного stop JVM чекпоинтит WAL, но копируем все три файла — безопасно в любом случае.

### D8. Rollback: два механизма
- Код: в compose оставляем предыдущий тег (`goodmood:<date>-<sha>`), откат = правка тега + `docker compose up -d`.
- Данные: restore файлов БД из последнего пред-деплойного бэкапа при остановленном контейнере.
Teardown-миграции (.down) — ручной аварийный инструмент (через nREPL `-m nrepl.cmdline` / отдельный `-e` вызов migratus), в автоматике деплоя не участвуют.

### D9. Доступ наружу: reverse proxy DSM
Правило `goodmood.<домен> → localhost:3000` + сертификат DSM — настраивается вручную на NAS один раз, в репозиторий не входит. Приложение слушает HTTP внутри LAN, TLS терминирует DSM. WebSocket'ов нет (htmx polling), прокси-конфиг тривиален.

## Risks / Trade-offs

- [Миграция падает на старте прод-БД → контейнер в crash-loop] → health-check в deploy.sh возвращает non-zero; откат = restore бэкапа + предыдущий тег образа. Прогон миграций на копии прод-БД (или свежей БД) перед деплоем.
- [2 ГБ RAM на NAS: JVM + Container Manager + FreshRSS + …] → `-Xmx384m` + `restart: unless-stopped`; следить за свободной памятью на первом деплое.
- [docker group = root на NAS при компрометации ноут-сессии] → приемлемо для домашнего LAN-хоста с одним админом; альтернатива — пароль в sudo раз в деплой.
- [Squash теряет историю схемы] → история живёт в git-истории миграций до архива ветки; финальная схема эквивалентна — проверяется подъёмом с нуля.
- [Потеря NAS-тома = потеря данных] → вне скоупа; bind mount позволяет подключить Hyper Backup DSM позже.
- [dotenv-библиотека с Clojars мала/заброшена] → проверка активности при выборе; запасной вариант — 15 строк парсера в одном неймспейсе.

## Migration Plan

1. Env-конфигурация (dotenv, `GOODMOOD_PORT`/`GOODMOOD_DB_PATH`, `bin/dev`, `.env.example`) — dev продолжает работать как раньше.
2. Squash миграций + seed-рыба — удалить dev-БД, проверить `clj -M:dev` с нуля, прогнать e2e smoke.
3. build.clj + `:build`, Dockerfile, compose.yaml — собрать образ, прогнать локально (`docker run` с bind mount во временный каталог), проверить health-check и миграции с нуля.
4. deploy.sh + настройка NAS (docker group, каталоги, .env на NAS, stack, reverse proxy) — первый деплой на чистой БД, проверка рыбы и авторизации.
5. Правила миграций → AGENTS.md; README-секция «Деплой».

Rollback ветки: каждый шаг независим; до шага 3 прод-данных не существует, после шага 4 действуют D8-механизмы.

## Open Questions

- Конкретная dotenv-библиотека и версия tools.build — зафиксировать при имплементации (конвенция: последняя версия).
- Scheduled-ежедневный бэкап через Task Scheduler DSM — опциональное продолжение, не в этом change.
