# Design: add-entries-crud

## Context

Записи (`entries`) сейчас create-only: в `app.db.entries` — `create-entry!`/`get-entries`/`set-state-label!`, в `app.routes.entries` — POST (create) и legacy GET (redirect на /feed), в `app.views.entries` — мёртвый фрагмент карточки. CRUD-паттерн уже отработан на инсайтах: in-place edit (`GET /insights/:id/edit-context` → форма → `POST /insights/:id/context` → свап outerHTML), confirm-модалка удаления (daisyUI `dialog`, `hx-delete` с CSRF-заголовком), владение через `user_id` в WHERE. Все колонки для редактирования уже существуют (миграции 004/006).

## Goals / Non-Goals

- Goals: посмотреть/отредактировать/удалить любую свою запись; список с переходом из шапки ленты; переиспользование готовых паттернов (insights CRUD, PageShell, ленточная группировка).
- Non-Goals: пагинация, массовые операции, audit log, редактирование `state_period_id`, импорт/экспорт.

## Decisions

### D1. Один роут обновления вместо поля-за-полем

Edit: `GET /entries/:id` (страница-карточка с read-блоками) + `POST /entries/:id` (update любого подмножества полей, Malli-схема с опциональными ключами) + `DELETE /entries/:id`. Удаление/правка инлайном из списка — только через карточку (меньше точек входа, меньше OOB-свапов).
- Альтернатива (поле-за-полем, как в insights): даёт мелкие свапы, но удваивает число роутов ради редкого сценария. Запись редактируется целиком («опечатка в заметке» = открыть карточку).
- Удаление из списка — тоже через карточку; в списке только просмотр.

### D2. Владение и удаление — жёсткое, без каскадов

`WHERE id = ? AND user_id = ?` в update/delete/get-one (чужой id → 0 строк → 404). Удаление — `DELETE FROM entries WHERE ...` без каскадов: `state_period_id` других записей и `ai_findings` не трогаются. AI-анализ просто перестаёт видеть запись.
- Риск-оценка: медикаментозные логи линкуются по дате (`medication_logs.entry_date`?) — по спеке «Medication logs link to entries by date», не по FK, удаление записи их не ломает.

### D3. Список — серверный рендер полной страницы, без бесконечной прокрутки в v1

`GET /entries` рендерит все записи пользователя (у реального юзера — сотни, страница лёгкая: текст + чипы). Группировка по дате переиспользует паттерн ленты (`group-by :date`, day-header).
- Альтернатива (htmx-подгрузка пачками): YAGNI до появления реальных проблем с объёмом; добавляется, когда понадобится.

### D4. Формы — как в чек-ине, но POST (не htmx-create)

Edit-форма ядра: слайдеры `gm-range` (те же компоненты `range-field`-стиля), дата — нативный `<input type="date">`, сон — number, заметка/активность — textarea/input, state_label — select розы ветров + свободный текст (как в фиде не редактируем — select стандартных + пусто). Отправка — обычный `hx-post` с json-enc на `POST /entries/:id`, свап обновлённых read-блоков; при ошибке валидации — мягкий alert в блок формы.

### D5. Точка входа — иконка в шапке /feed

Рядом с заголовком «Лента» иконка `list-bullet`/`stacked` → `/entries`. Нав (5 пунктов) не трогаем — решение зафиксировано в разведке.

## Risks / Trade-offs

- [Удаление записи необратимо и меняет будущие AI-анализы] → confirm-модалка с явным текстом; жёсткое удаление выбрано сознательно (мягкое + тумблер «показать удалённые» — overkill для v1).
- [POST /entries/:id с частичными полями может стереть незаполненные] → update-схема строит SET только из переданных ключей; пустая строка ≠ отсутствие (пустая строка = очистить поле — задокументировать в хелпере).
- [Дублирование компонентов слайдеров между check-in и entries] → слайдеры check-in — приватные функции view; для карточки редактирования допускается локальная упрощённая версия (input+значение), либо вынос общего компонента — решить по месту, не тащить абстракцию заранее.

## Migration Plan

Без миграций. Роуты регистрируются в `routes/app.clj` рядом с существующим `/entries`; legacy `GET /entries` redirect заменяется страницей списка — обратной несовместимости нет (редирект был временным костылём). Откат — предыдущий тег деплоя.

## Open Questions

- Нет. Владение, жёсткое удаление и объём редактируемых полей подтверждены в разведке; если при имплементации всплывёт конфликт с медикаментозными логами — поднять вопрос отдельно.
