# Design: add-entry-date-picker

## Context

Колонка `entries.date` (TEXT ISO-дата) уже существует; `create-entry` всегда пишет туда серверную `(today)`. Путь редактирования уже принимает `:date` (regex `^\d{4}-\d{2}-\d{2}$`, views/entries.clj:236 использует нативный `<input type="date">`). `get-entries` сортирует по `date DESC, created_at DESC` — бэкфилл сам встаёт под свою дату. State-периоды хранят `started_at`/`ended_at` (TEXT datetime); сейчас запись привязывается только к *активному* периоду (`get-active-period-id`, Decision 6.1).

## Goals / Non-Goals

**Goals:**
- Бэкфилл записи на выбранную дату в диапазоне [сегодня−30; сегодня].
- Ноль новых зависимостей, ноль миграций, ноль JS.
- Привязка записи к периоду, накрывающему выбранную дату.

**Non-Goals:**
- Валидация даты на edit-карточке (остаётся как есть).
- Клиентское время/таймзоны — всё по серверным часам, как слот-пуши.

## Decisions

1. **Нативный `<input type="date">` в реюженном `optional-block`** — а не CSS-пикер или hyperscript-календарь. Android уже даёт системный пикер; паттерн collapse+disabled уже в файле; unchecked → disabled → поле не сабмитится → сервер ставит today. Дефолтное значение input = серверная today (не пустое) — если юзер откроет блок и не поменяет дату, отправится корректное сегодня.

2. **Границы даты: HTML-атрибуты + серверная валидация.** `min`/`max` на input дают UX-подсказку (пикер не даст выбрать вне диапазона), но граница доверия — сервер: `create-entry-schema` валидирует `[:date {:optional true} [:maybe [:and string? #"\d{4}-\d{2}-\d{2}" ...]]]` c проверкой `<= today` и `>= (today − 30)` malli-кастом-предикатом (константа `max-backfill-days 30` в домене). Невалидная дата → 400 с текстом ошибки в `#form-error`, как остальные ошибки формы.

3. **Точка правды даты — домен:** `(or date (today))`. Route просто пробрасывает `:date`; пустая строка/absent → today. Одна строка в `create-entry`, никакой дублирующей логики.

4. **Привязка периода по дате:** новый запрос `app.db.state-periods/get-period-covering-date` — `WHERE user_id = ? AND date(started_at) <= ? AND (ended_at IS NULL OR date(ended_at) >= ?)` (SQLite `date()` нормализует datetime до дня: запись датой «02.09» цепляется к периоду, начавшемуся 02.09 в 09:00). Fallback: не нашли накрывающий → берем активный (сегодняшний) — текущее поведение для записей вне всех периодов сохраняется. `get-active-period-id` остаётся для остальных вызовов.
   - Альтернатива: оставить привязку к активному всегда — отвергнуто: бэкфилл в закрытый эпизод, прицепленный к текущему периоду, искажает статистику эпизода.

5. **`created_at` не трогаем.** Запись создана сегодня — `created_at` честно «сегодня»; сортировка внутри одного дня (несколько записей за бэкфилл-дату) — по created_at, это ок. Опциональный `:created-at` в `db/create-entry!` остаётся нетронутым.

## Risks / Trade-offs

- [Бэкфилл меняет «последнюю запись» → away-баннер и soft-mode могут отреагировать неожиданно] → last entry определяется по `date DESC, created_at DESC`; бэкфилл вчерашней становится «второй». Проверить глазами в e2e-сценарии; правки логики не ожидается.
- [30-дневный лимит — магическая константа] → Именованная константа в домене, одна правка если решим расширить.
- [Радар периода с бэкфиллом за окно >30 дней] → Радар окно максимум 30 дней (month); записи старше окна просто исключаются фильтром — поведение уже корректно.

## Migration Plan

Без миграций. Деплой обычный; откат — обычный rollback (схема не менялась).
