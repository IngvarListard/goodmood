# Структура проекта

Слоистая архитектура. Каждый слой знает только о слоях "ниже" себя. Поток вызовов: `routes` → `domains` → `db`, результат идёт в `views`.

## src/app/db/

Единственное место, где есть SQL/JDBC-запросы.

- Функции доступа к данным: `get-user`, `insert-order!`, `list-locations`.
- Настройка/жизненный цикл соединения (datasource, пул).
- Только чистые функции "данные → данные".
- ЗАПРЕЩЕНО: hiccup, HTML, ring-request/response, reitit.

## src/app/routes/

Диспетчеризация HTTP-запросов. Клей между слоями, без бизнес-логики.

- reitit-таблица маршрутов (`["/path" {:get {:handler ...}}]`).
- Хендлеры: принимают `request`/`system`, вызывают `domains`, передают результат в `views`, возвращают ring-response.
- Middleware, специфичный для конкретных роутов (auth, парсинг параметров).
- ЗАПРЕЩЕНО: прямые SQL-запросы, бизнес-правила, построение сложной разметки внутри хендлера.

## src/app/views/

Только рендеринг HTML. Никакой логики принятия решений.

- Hiccup-функции, принимающие готовые данные аргументом и возвращающие hiccup-разметку.
- Общий layout, шапка/футер, переиспользуемые UI-компоненты.
- HTMX-фрагменты (partial-респонсы для ajax-запросов).
- ЗАПРЕЩЕНО: вызовы `db/*`, бизнес-валидация, запросы к БД.

## src/app/domains/

Бизнес-логика предметной области. Не знает про HTTP, reitit, hiccup.

- Чистые функции бизнес-правил и валидации (`orders/calculate-total`, `orders/can-cancel?`).
- Оркестрация: может вызывать `db/*` для чтения/записи.
- Spec/malli-схемы данных.
- ЗАПРЕЩЕНО: ring-request/response, hiccup, reitit-роуты.

## Правила при написании кода

1. Не импортировать "снизу вверх": `db` не должен требовать `routes`/`views`/`domains`.
2. Новую бизнес-логику класть в `domains/`, а не в хендлер роута.
3. Вьюха всегда принимает готовые данные, а не сама их достаёт.
4. Один домен — одна поддиректория в `domains/` (вертикальный срез по фиче, не по техническому типу).
